# GPU server setup

Routes: any route that rents a box. Blender-slot rules: 3d-sprite, redesign (render), map props; Hunyuan rules: 3d-sprite, 3d-realtime, redesign (meshing). Origin: aroa unless tagged otherwise (orin = an earlier 3D character project).

## Sizing an offer (read before renting)
- **Blender sprite rendering is CPU-bound.** Measured: 8 Blender processes on 64 cores pegged the CPU (load 208, steal 41 %) while the GPU sat at 10–34 %; each process used ~8 cores, 0.6–1 GB VRAM, 1.2 GB RAM. So **Blender slots = effective vCPU / 8** is the safe starting point, and offers are compared by **$ per effective vCPU-hour**, not $ per GPU. (aroa)
- **Then measure and tune the cap on the live mix; cores/8 can leave half the box idle.** On a 1× RTX PRO 6000 box (61 cgroup CPUs), the per-body hair/face/item layer mix used only **~2.5 cores per Blender process** (`blender -t 8`). At 7 slots the box was 72 % idle with 0 cgroup throttling. Measured (distinct frames/s for the whole box; s/frame per process) (aroa):

  | slots | frames/s | s/frame per process | cores used |
  |---|---|---|---|
  | 7 | 30.8 | 0.23 | 18 |
  | 14 | 67.6 | 0.20 | 34 |
  | 18 | 58.0 | 0.30 | 41 |

  At 18 the per-task render time rose as fast as the slot count, so throughput plateaued: the single shared GPU (53–90 % busy) became the limit, not the CPU. Keep the best measured setting (here **14, so cores/slot ≈ 4**). Set it as a measured cap (aroa: `FLEET_BL_TOTAL` + `FLEET_BL_SLOTS` (the per-GPU clamp of 8 would hide it) + `FLEET_BL_THREADS=8` in `fleet.env`). Judge each step by box frames/s from files actually written plus per-task seconds of the same kind, never by slot count. Measure over ≥ 5 min after a 2 min warm-up, and take a union of periodic `find`s, because harvest loops delete finished sets mid-window (kit `tools/fleet/box/measure_tp.sh`).
- **Benchmark seconds/frame per process AT FULL CONCURRENCY before scaling a box type, and compare offers by measured frames/s per $** — not vCPU or GPU count. The cores/8 rule above held on RTX PRO 6000 64-vCPU boxes (~0.2 s/frame per process, ~36 frames/s per box at ~$1.3/h) and on RunPod RTX 6000 Ada (~0.2 s/frame). It failed on 8× RTX 5090 containers with driver 615: 0.3 s/frame with 8 renders, but **~2.9 s/frame with 61** (Vulkan or OpenGL, 1 or 4 per GPU alike), 95 % CPU idle, Blender threads in `D` state inside a machine-wide driver lock (`os_acquire_rwlock_write`) — ~3–4× worse frames/s per $ than the PRO 6000 box, not fixable inside the container. Gate: refuse a box whose full-slot benchmark is > 0.5 s/frame per process (aroa; kit `tools/fleet/verify.sh` step 6).
- **Effective vCPU is the cgroup quota, not `nproc`.** A RunPod box showed `nproc` 128 but a quota of 27 CPUs (= 3 slots). Read it before trusting any listing (aroa):
  ```bash
  if [ -r /sys/fs/cgroup/cpu.max ]; then read q p < /sys/fs/cgroup/cpu.max            # cgroup v2
  else q=$(cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us); p=$(cat /sys/fs/cgroup/cpu/cpu.cfs_period_us); fi
  [ "$q" != max ] && [ "$q" -gt 0 ] && echo $((q / p)) || nproc
  ```
  Under a quota, give Blender `-t 8`, or every process starts `nproc` threads and thrashes.
- **Hunyuan3D-2.1 needs ~28–30 GB VRAM and 24–32 GB RAM per process**, ~70–90 s per mesh, ≤ 2 processes per GPU (48 GB+), model load ~2–5 min. A 24 GB card cannot run it; a **32 GB card runs exactly one** (measured 24–28 GB on a 5090) with ~1 Blender beside it — restrict Hunyuan to a few GPUs (aroa `FLEET_HY_GPUS`) or every card fills and frames/s collapses. Plan ≥ 48 GB cards.
- **Few big GPUs + many cores beats many small GPUs.** Hunyuan finishes early and then the GPUs idle; Blender (CPU) sets the wall time. Avoid 8× 24–32 GB consumer cards with ≤ 96 vCPU. (aroa)
- **RAM** ≈ 1.5 GB × Blender slots + 32 GB × Hunyuan processes + 16 GB. **Disk** ≥ 200 GB for a production wave (Hunyuan weights 18.5 GB, venv 3 GB, Blender 1.6 GB, ~23 MB per rendered layer set incl. its .blend); refuse a box with < 60 GB free. (aroa)
- **Network:** test HuggingFace and GitHub from the box in the first minutes (Hunyuan setup clones GitHub and downloads release assets from it; weights come from HF). Some hosts block or crawl on them: destroy and pick another rather than fight it. Pin weight revisions; HF `main` moves, so a new box can silently get different weights than the reference box. (aroa)
- Example plan (aroa wave 2, ~4,700 layer sets + 250 meshes, planner estimates): 4× ≥ 48 GB GPUs, ≥ 192 vCPU, ≥ 384 GB RAM, 200 GB disk ≈ 4 h; or 12 RunPod pods of 2× L40 / 64 vCPU ≈ 2.4 h. Check every listing's real cgroup quota after boot (that RunPod test pod had 27 of 128).

## Bring-up (one box)
1. **Before renting:** concepts for the wave are generated (GPT runs on the dev machine; no API key ever goes to a box), and if the work is body layers, the pose release is frozen or close. Run the planner for an ETA (`fleet.py plan`). (aroa)
2. **Rent and alias** it in `~/.ssh/config`; no public ports. On Vast, read `/etc/vast-agents-guide.md` first and keep a copy next to the box's logs. (aroa)
3. **Probe** into JSON: provider, GPUs + compute capability, EGL libs, cgroup CPUs, RAM, disk, `workspace_is_volume`, running GPU processes. Fail on no GPU, < 8 GB VRAM or < 60 GB disk. (aroa)
4. **Free the GPUs:** images that auto-start servers (Vast vLLM image: vLLM on every GPU, ~88 GB each) must be stopped; `supervisorctl stop vllm` leaves `VLLM::Worker_TP*` orphans holding ~30 GB per GPU — kill them by PID. (aroa)
5. **Blender:** pinned tarball under its original filename (`sha256sum -c` matches by filename), same version as the dev machine. (aroa)
6. **EEVEE health + GPU pinning:** render a test on the *last* GPU and see in `nvidia-smi` where it actually landed. EEVEE uses EGL, which may ignore `CUDA_VISIBLE_DEVICES`. Outcomes: `cuda` (pin works), `vulkan` (`--gpu-backend vulkan --gpu-device N`; frames may differ slightly from OpenGL, so compare with a tolerance), `none` (all Blender on GPU 0, other GPUs do Hunyuan; fine because Blender is CPU-bound). Compute-only containers lack `libEGL_nvidia` and EEVEE **silently falls back to CPU Mesa**: install the userspace libs from the exact driver `.run`, or drop the box. (aroa)
7. **Hunyuan venv:** copy a built venv only when OS, Python, torch and GPU arch match (sm_120 vs sm_89 differ); otherwise build in the background (~15–20 min) and start Blender work meanwhile. (aroa)
8. **Weights and data:** measure HF vs direct box-to-box vs relay through the dev machine, take the fastest; copy snapshots/bodies/meshes and compare every `.blend` sha256 with the source. Run content checks too (aroa: head-socket height check stops the bootstrap on stale bodies).
9. **Verify** (step 9 is the gate; then the full-concurrency frames/s benchmark, refuse > 0.5 s/frame per process): one known layer set rendered on every GPU at once through the real path. Pass = each process ran on its assigned GPU, all GPUs byte-identical (or within tolerance for vulkan), equal to the reference box's frames, `check_edges` green, timing recorded. Record a pass per GPU model and pose tag; never send work to an unverified model. (aroa)
10. **Start the worker and a pull loop** (every 10 min). Done when probe.json, a verify PASS and a running pull loop exist. (aroa)

Re-running bootstrap must resume (every step skips what is done). Long ssh renders: background them or keep local timeouts > 10 min.

## Slots and locks (rules)
- Blender per GPU: **8 slots without Hunyuan, 6 while a Hunyuan runs on it** (aroa measurement), also capped by VRAM `(VRAM − 30 GB × hunyuan − 2 GB) / 1 GB` and box-wide by effective CPUs / 8 — a default to confirm with the benchmark; where the box is latency/driver-bound instead of CPU-bound, set the cap from measured box frames/s (aroa `FLEET_BL_TOTAL`, `FLEET_BL_SLOTS`). A waiting Hunyuan reserves its VRAM so Blender can't starve it.
- Hunyuan per GPU ≤ 2, only with ≥ 30 GB free VRAM and ≥ 24 GB MemAvailable, starts staggered 40 s (RAM spikes at model load). (aroa)
- **One short rental for a meshing-only round** (aroa A213): prep every input locally (cutouts, per-item face budgets, a staged job list that can be regenerated right before renting), then run all stages under one hy.lock hold ordered by value (items shown in game → map objects → icon-only items, which may drop to 5–8k faces / octree 256 / tex 1024), pull after each stage, and gate "safe to destroy" on a file-by-file size comparison. Measured: 2 processes on one Blackwell card (12k faces, octree 384, tex 2048) = ~35 s wall per item incl. model load (133 items in 77 min). Resume must skip finished stages before loading the model (~5 min per load). Put the stage whose inputs are still being drawn LAST and let it "follow": each pass meshes only the pending inputs (hard links into a pass dir keep the shards balanced), then it polls for inputs pushed into the running box (rsync without --delete) until a FINAL marker; push late inputs in batches (each pass reloads the model). Test the box script with a fake `batch.py` that copies old meshes, and the dev side with a fake ssh, before renting. (aroa)
- Remote "is it still running" checks: `pgrep -f '[b]atch.py'` (bracket trick), or the check matches its own `bash -c` command line and reports busy forever. (aroa)
- Slots are `flock` files; caps are recomputed on every acquisition, so running jobs are never interrupted. Close the lock fd for the child command so a stray background child can't hold a slot. Hunyuan holds one global lock (`flock /root/kit/hy.lock`). (aroa)
- Kill by PID from the assign log or `nvidia-smi`. **`pkill -f` / `pgrep -f` match their own command line** (a wait loop killed itself twice; orin killed its own ssh); always use PIDs. Same trap in a remote guard `ssh box 'pgrep -f worker.py || start worker.py'`: the ssh `bash -c` line contains the pattern, so the guard always "finds" it and never starts the worker (aroa: B2 sat idle 50 min after the box returned). The `[w]orker` bracket trick is not enough there either: the start command later in the same `bash -c` line contains the plain name. Anchor on the process's own argv (`ps -eo args | grep -q "^python3 pipeline/[w]orker.py"`) or use a PID file.
- Sharing one box between agents: give each worker a live cap on top of the box slot manager: a wrapper takes one of `locks/s1..N.lock` (N read from a small file on every acquisition) before calling the slot manager. Lowering N then frees slots within one job length without restarting the worker, and the wrapper path can even be swapped under a running driver that calls it per job (aroa A070: riders hold 12 of 14, 2 left for another agent's rehearsals). Hand the box over between agents with flag files in a queue script (`KNIGHT.done` → other agent runs → `POSEV3.done`), not with timing.
- sshd `MaxStartups` resets bursts of sessions: stagger ssh starts ~0.7 s, ≤ 8 at a time; better, run the worker on the box itself. A reset is silent job loss (aroa: 14 of 32 parallel head jobs vanished): retry when ssh exits 255 with `kex_exchange`/`Connection reset` in stderr (back off 2 + 3·i s), and have remote "is it done?" checks echo an explicit marker so a failed login isn't read as "not done".

## No persistent volume
- Destroy (and RunPod "stop") wipes the container. Pull continuously; keep a **local mirror** of what a new box needs (pose snapshots, body blends, weapon meshes, runtime copies) with a sha256 index, refreshed after every body or snapshot change, so a dead box costs one re-seed, not the project. (aroa)
- On Vast containers `/root` is the overlay and a container restart wipes it (aroa: a Hunyuan run was lost this way). Write any batch output that must survive a restart to the persistent volume (`/workspace/<dir>` with a `/root/<dir>` symlink), and make box-side drivers resumable (skip finished sets, per-item done markers) and self-pausing on a free-space floor, since a fleet disk guard only stops fleet workers.
- Don't re-save mirrored blends after seeding: a new sha256 invalidates the fleet's copy checks and done-markers. (aroa)
- **Teardown** (checklist, destroys nothing itself): no worker running → final pull of every wave → no key/.env on the box → then destroy in the console. Vast "stop" still bills storage. (aroa)
  - A long-lived box collects ad-hoc lanes outside the wave layout. Before destroying it, sort every top-level dir into: (a) seed or install you can re-create, (b) output already local, (c) output that is only on the box. Compare with `rsync -rn --size-only --itemize` (read-only). Where local packing or publishing changed the layout, compare per set: is the set published, and does its frame list match? Then pull only class (c), with `rsync -a --size-only --compare-dest=<local equivalent>/` into a dated archive. On one box this came to 1.4 GB of logs, timings, configs and on-box pipeline patches, against 150 GB on disk.
  - Run the compares serially or two at a time: many parallel ssh sessions to one Vast box get `Connection reset`, so a compare can come back as a false "0 missing". Check rsync's exit code. Never `pkill -f`/`kill $(pgrep -f <pattern>)`: the pattern also matches your own shell and wait loops. Kill by the PID you looked up.

## Provider differences
| | Vast.ai | RunPod |
|---|---|---|
| Guide | `/etc/vast-agents-guide.md`, `vast-capabilities` | none; detect via `RUNPOD_*` env / `/etc/rp_environment` |
| Services | supervisor; image may auto-start vLLM | no systemd: `setsid nohup` everything |
| SSH | one alias per box | port differs per pod, IPs reused with new host keys → separate `known_hosts`, `accept-new` |
| EGL | usually present; `install-display-drivers` | often compute-only → extract EGL libs or drop the pod |
| CPU | quota usually ≈ listing | quota can be far below `nproc` |
| Disk | container disk | small container disk; move work dirs to `/workspace` volume via symlinks so paths stay identical |
| Stop | keeps disk, still bills storage | wipes container disk: never stop mid-wave |

## Gotchas
- **Changing a running queue script:** bash reads a script while it runs, so editing it in place corrupts the running queue. Upload the new version under another name and `mv` it over the old one (new inode; the running bash keeps the old one), kill the old queue bash by PID (its foreground driver keeps running), and start the new queue with a guard in every step: wait while a driver of the same kind is still running, then rerun it (resumable drivers skip finished work). Never two drivers at once. (aroa)
- **Gate filters in shell:** `grep FAIL | grep -v "not found$"` also matches the gate's summary line (`... FAILED, 2 problems`) and turns expected `base ... not found` lines into a false rehearsal failure (aroa: the B3 queue stopped and idled). Anchor on the line start (`grep "^FAIL"`).
- **Image services restart with the box.** vast's vLLM image autostarts a supervisor `vllm` service at boot; after a restart it held 88 of 98 GB VRAM and every Blender job became ~3.5× slower (1,100 s instead of 230–320 s), with no error anywhere. After any box restart, check `nvidia-smi` for foreign processes and compare job durations with the pre-restart median before trusting the ETA. Stopping it (`supervisorctl stop vllm`) is an owner decision when the box is shared. (aroa)
- A Hunyuan process that vanishes without a traceback ran out of RAM (check `ps`, not the log). It leaks `/tmp/tmp*.ply` (~45 MB per mesh): run a cleaner. (aroa)
- Long single rsyncs break with a broken pipe: pull per set with retries. (aroa)
- **Remote wrappers in `--rsync-path` break rsync:** `--rsync-path='nice -n 19 ionice -c3 rsync'` dropped every transfer after a few MB (broken pipe); `nice -n 19 rsync` alone is fine. Throttle with `--bwlimit` instead. (aroa)
- **Many small files over ssh:** per-file round trips dominate (a 9 MB tree of a few thousand PNGs stalled in rsync/scp for minutes); `tar czf` on the box + one `scp` took 5 s. (aroa)
- **Slot count is a measurement, not cores / per-slot:** on a 46-core-quota PRO 6000 box with ~2.5 cores per Blender, 11 slots (-t 4) gave 3.13 PNG/s and 14 slots (-t 3) 2.44 PNG/s with more cgroup throttling, while only ~18 of 46 cores were busy; short jobs are bound by per-job startup and I/O. Measure frames/s and throttled periods over 10 min per setting and keep the faster one. (aroa)
- **A second box needs an acceptance render before it gets work:** re-render one job the first box already finished and diff the frames (`imgdiff.py`); aroa box 2 (driver 580 vs 595) came out byte-identical on 1,802 frames.
- Home uplinks are slow (0.3–0.8 MB/s); intercontinental TCP to some pods crawled at ~13 KB/s per stream. Seed the first box once, fan out box-to-box, use many parallel streams. (aroa)

- **Noisy-neighbour memory pressure:** on a shared host, PSI memory `full` of 50–80 % made builds stall at random (2 s → 2,000 s) with nothing wrong inside the container. Read `/proc/pressure/memory` in verify and during waves; send light lanes (icons, packing) to a pressured box and heavy builds elsewhere. (aroa A116 release lead)
- **The local disk watchdog must not stop agent shells:** a watchdog that SIGSTOPs every process whose command line names a pull also froze an agent's zsh that only mentioned it, hanging the agent. Skip `zsh` (and other shells), and exempt pulls whose output lands on a separate data disk via an explicit list. (aroa A116; kit v3 `tools/fleet/disk_watchdog.sh`)
