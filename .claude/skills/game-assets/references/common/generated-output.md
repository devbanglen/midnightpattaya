# Where generated output lives (all routes)

Applies to every route: renders, pulls, published sets, map packs, build output, downloaded asset libraries and their
conversions. The kit sets this up at `kit/init_project.sh` time (`<parent>/<name>-art`, `<parent>/<name>-studio-out`,
symlinked back as `art/`, `studio/public`, `studio/dist`).

## Outside the project, low-dir, one copy
aroa, 2026-10-10: Workspace Deck (an IDE/agent dashboard) inotify-watches every dir of a project at startup and hung on ~1.5M sprite dirs (`max_user_watches` 524288, ENOSPC, ~20 GB of memory). The next day the same output, kept up to 3×, filled the drive holding the WSL vhdx and WSL crashed.
- **Generated output never lives inside a watched project path.** Renders, pulls, published sets and build output go to a sibling tree (`~/projects/<game>-art`, `~/projects/<game>-studio-out`) and are symlinked back, so tool paths stay the same. (aroa)
  - Every publisher and pull loop first calls a guard that fails when a link is missing, dangling or replaced by a real folder (kit `tools/guard_symlinks.py`). Otherwise `os.makedirs(..., exist_ok=True)` / `mkdir -p` silently recreate a real tree inside the project.
  - `rsync --delete` into a link: end the destination with `/`. Never `rm -rf <link> && mkdir <link>`. Restore tars under a link with `--keep-directory-symlink`.
- **Low-dir layout from day one.** `<set>/<clip>/<dir>/<layer>/<key>.png` is 1 + C + 8C + 8CL dirs per set: 326 dirs for 785 files (~2.4 files/dir). Use one trimmed atlas per clip plus a JSON frame map (1 dir, ~15 files per set; also what a web client wants), or at least flat names `<clip>/<dir>_<layer>_<kk>.png`. (aroa)
  - If the renderer is part of the pose hash, pack after render (on the box, before pull) instead of editing the renderer.
- **Backups to a Windows drive from WSL (drvfs/9P):** stream tar straight to the drive (no local temp copy), but gently: parts of ≤ 5 GB with their own sha + id list (resume by part), throttle to ~8 MB/s, pause ~30 s between parts, and a stall watchdog (a .part that stops growing for 3 min pauses the chain and notifies; no auto-retry). Sustained full-speed writes to /mnt/c preceded two WSL crashes in aroa. Verify with one throttled read per tar that both hashes and lists it (sha + manifest count).
- **Budget** (check it in the gate): ≤ 2 dirs per set; ≤ 50k dirs and ≤ 1 copy of each finished set in the whole output tree. Measure with `du --inodes` on subtrees, never with repeated full-tree `find`. Delete raw and intermediate copies once the published copy has the same pose_version and frame count (kit `tools/cleanup_published_raw.py`, run by every publisher). Watch the free space of the drive that holds the VM disk, not just the free space of `/`. (aroa)

## Staging trees that symlink published sets
A bench/pack staging tree that links published set dirs "read-only" is a write path into the published tree: `rmtree(link, ignore_errors=True)` leaves the link and the next pack writes through it (aroa 2026-10-13: 15 bodies overwritten). Writers must `unlink` links and refuse any destination whose realpath lands in the published tree. Recovery is cheap only if every set has a verified backup and a pre-incident stat record (size + mtime per manifest/atlas from the release plan): extract the sets to a temp dir, match the stat records, swap the dirs under the index lock, re-gate. Find damage two ways: mtimes in the incident window, and content markers the writer adds (new layers, pose code).

## Publishing onto a second disk via per-set links
When the disk holding the published tree runs low (WSL: the vhdx host drive), (kit v3: `tools/release/datadisk.sh`, `pub_link.py`, `index_merge.py`) publish new sets onto another native disk and leave a per-set symlink `<published>/<id> -> <data disk>/pub/sets/<id>`: copy to `<id>.tmp` outside the index lock, then rename + link under it; the replaced real dir is renamed aside on its own disk (no bytes written). Before relying on it, test every consumer through a link on a scratch tree: the gate, the deploy-pack builder, the release plan/verify/freeze, the dev server's static dir (Vite follows links). Two traps: `tar -c` stores the link, not the files, so backups must dereference (`tar -h`); write guards that compare realpaths must also list the data-disk root as protected. Links dangle when the second disk is not mounted, so the plan must report missing files. Estimate the publish's local writes first: a same-fs rename costs 0, packing raw v1 staging writes the full packed size, cross-disk staging is a copy, and old sets kept aside free nothing. Source: aroa `tools/release/pub_link.py` (A116).

## Moving a running render release onto a second disk
When the host drive fills mid-release (a pull watchdog pauses pulls), switch the release's new output, not its old trees. (1) Point each still-to-render manifest's `local_root` at a new dir on the data disk (created as a symlink back) before pushing it. Run one pull loop per manifest so a watchdog exemption regex can match its command line. Kill the old paused loops by PID: killing a stopped process needs SIGKILL. (2) The finalizer gets a shared sets dir plus a spill dir. Any set it writes from then on, new or re-finalized, goes to `<spill>/<id>` with a symlink in the shared dir, and the old real dir is deleted, so gates and ledgers keep reading one dir. Output that is a straight copy of its raw set (e.g. back items) is hard-linked when both are on the same disk, which halves the footprint. (3) A step that rewrites raw pages (a clip-limited merge) first moves that raw set to the data disk and links it back. (4) Renders that were finished but not pulled when the pause hit, and partial copies from killed rsyncs: compare per-tag file counts box against local. Fetch the incomplete tags with chunked `tar` over ssh (≈25 tags per stream, retry: a flaky link breaks large streams) into the data disk and link them in. Record count-verified tags in the same ledger the merge uses to trust raw copies. Estimate the GB per step first, and report it. (aroa A116, 2026-10-14)
- Smoke the new publish path end to end before the window on scratch copies: link two sets, merge a scratch index, build the real deploy pack from the linked overlay onto the target disk, then have the game server + client load it through the pack-dir symlink (static server follows links, traversal guard still holds) and run the e2e test. Keep the deploy-pack list gated on pose consistency (a layer whose pose code differs from its body never enters the pack): mixing new bodies with old layers in a smoke shows exactly that misfit. Source: aroa A116 smoke (pub_link + index_merge + parallel pack + slice e2e).
- Check each lane's staging *format* before the window, not only its content (kit v3 `tools/release/pack_stage.py` packs raw staging into fresh dirs): a raw v1 frame staging (`<clip>/` dirs, no atlas) must be packed before linking, or the publish ships an unusable layout that the per-file sha verify happily confirms (it only compares against staging). Pack into a NEW directory per set (delete any old output first, refuse a staging that is already packed unless its owner proves it fresh), verify pixel-exact, and publish from that packed dir; never "skip if an atlas exists" (a skipped pack shipped stale atlases once). For already-packed stagings, flag sets whose atlas/pages are older than the freeze of the pose snapshot they claim, unless the manifest carries a data-only restamp record (from -> to + proof); a restamp tool that forgets to write that record looks exactly like a stale set. Cost: full-body item sets pack at ~16 s CPU each (2,835 sets = 75 min at 8 jobs on a loaded 20-core box), so budget it in the window. Source: aroa A116 window, `tools/release/pack_stage.py`.
- Run every window step that can exceed the agent's tool time limit (deploy-pack build ~2 h, full gate ~1 h) fully detached (`setsid nohup … &`, log to a file, wait on the log), never as a background tool job: the job limit killed the v1 pack in its merge after the 4 workers had finished. Make multi-stage builds resumable (aroa `parallel.py --merge-only` redoes only the idempotent merge from the finished worker dirs: 7 min instead of 1.8 h). Keep the CPU free while the game team measures fps (crowd bench): run the heavy verify after their check.
- Backups when space is short: a full re-backup may not fit next to the new deploy pack; back up a *delta* (sets new or newer than the archive that holds them, + the index) against the last verified baseline, with the same part naming so the release plan counts it, and restore as baseline then deltas in order (aroa `tools/release/backup_delta.py`: 7,327 sets / 22.7 GB instead of 54 GB). A wave-based backup list must be derived from the index, not hard-coded, or a new publish wave is silently skipped. Decide "changed since the last backup" by content (sha256 of manifest/atlas/pages against the last freeze record), never by file mtime: a publish that copies with preserved mtimes (copy2/rsync -t) lands files older than the backup that came before it, and an mtime rule silently skips them (aroa v1.1: 855 of 1,755 changed sets found by mtime).
